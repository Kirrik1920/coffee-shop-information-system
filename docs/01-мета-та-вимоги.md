# 1. Мета та вимоги

## Бачення (корисність)

**Назва:** Інформаційна система обробки замовлень кав'ярні.

**Проблема.** У години пік замовлень стає більше, ніж бариста встигає приготувати.
Якщо каса напряму чекає на бариста, то збій або затримка на одному етапі зупиняє всю роботу.
Власник також не бачить, скільки замовлень чекає і де виникає затримка.

**Кому потрібна система:**

| Учасник | Тип | Що отримує |
|---|---|---|
| Клієнт (касир) | основна дійова особа | швидко оформлює замовлення |
| Бариста | основна дійова особа | отримує замовлення по черзі |
| Власник кав'ярні | основна дійова особа | бачить графіки й отримує сповіщення |
| Адміністратор | допоміжна дійова особа | запускає систему та стежить за сервісами |

**Користь.** Замовлення приймаються, навіть коли бариста тимчасово не працює, і не губляться.
Власник бачить стан роботи в реальному часі.

## Функціональні вимоги (можливості)

| № | Вимога |
|---|---|
| ФВ-1 | Система показує меню напоїв |
| ФВ-2 | Система приймає замовлення через HTTP і перевіряє напій та кількість |
| ФВ-3 | Прийняте замовлення передається в чергу RabbitMQ |
| ФВ-4 | Бариста-сервіс бере замовлення з черги по одному |
| ФВ-5 | Виконане замовлення зберігається в базі даних |
| ФВ-6 | Повторно доставлене замовлення не обробляється двічі |
| ФВ-7 | Система збирає метрики: створено, виконано, довжина черги, час приготування |
| ФВ-8 | Grafana показує метрики на дашборді |
| ФВ-9 | Система створює алерт, коли черга надто довга або сервіс не працює |

## Нефункціональні вимоги (властивості)

| № | Вимога |
|---|---|
| НФВ-1 | Система запускається однією командою `docker compose up -d --build` |
| НФВ-2 | Зупинка barista-service не заважає приймати нові замовлення |
| НФВ-3 | Замовлення зберігаються в черзі після перезапуску RabbitMQ (durable-черга, persistent-повідомлення) |
| НФВ-4 | Метрики оновлюються не рідше ніж раз на 5 секунд |
| НФВ-5 | Алерт спрацьовує не пізніше ніж через 1 хвилину після проблеми |
| НФВ-6 | Веб-інтерфейси доступні лише з цього комп'ютера (127.0.0.1) |

## Межі проєкту

**Входить:** прийом замовлення, черга, імітація приготування, збереження, моніторинг, алерти.

**Не входить:** оплата, реєстрація клієнтів, мобільний застосунок, облік складу.
Ці функції винесено за межі проєкту, бо вони не потрібні для основного ланцюжка обробки замовлення.

## Сценарій використання: «Оформити замовлення»

| Поле | Значення |
|---|---|
| Дійова особа | Клієнт (касир) |
| Мета | Передати замовлення на приготування |
| Передумова | order-service і RabbitMQ працюють |
| Основний потік | Клієнт надсилає напій і кількість; система перевіряє дані; замовлення потрапляє в чергу; клієнт отримує номер замовлення |
| Альтернативний потік | Напою немає в меню: система повертає помилку 400 |
| Виняток | RabbitMQ недоступний: система повертає помилку 503 |
| Постумова | Замовлення лежить у черзі `orders` |

## Чому RabbitMQ, а не Kafka

| Критерій | RabbitMQ | Kafka |
|---|---|---|
| Завдання проєкту | черга завдань: кожне замовлення виконує один бариста | потік подій, які читають багато споживачів |
| Після обробки | повідомлення видаляється | повідомлення зберігається |
| Підтвердження обробки | вбудоване (ack) | через зсув (offset) |
| Простота запуску | один контейнер із веб-панеллю | складніше налаштування кластера |

Обмеження навчальної версії: обидва сервіси підключаються до RabbitMQ одним обліковим записом.
У реальній системі кожен сервіс мав би власний, як радить лекція 9.
