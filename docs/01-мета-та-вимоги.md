# 1. Мета та вимоги

## Відповідність завданню курсу

Завдання «Опис завдання для Створення прикладної Інформаційної системи»: система забезпечує отримання даних про роботу з базою даних, відображає їх через Grafana та використовує Prometheus для збору й обробки метрик. Доступ до системи можливий лише для авторизованих користувачів.

| № | Вимога завдання | Реалізація |
|---|---|---|
| 0 | СУБД у Docker-контейнері | PostgreSQL 16, сервіс `postgres` |
| 1 | Генерація та актуалізація даних у БД програмними засобами | `barista-service` (Python, psycopg), `scripts/send-orders.ps1` |
| 2 | Збір даних через Prometheus | `postgres-exporter`, метрики сервісів |
| 3 | Зберігання в Time Series Storage | вбудована БД Prometheus |
| 4 | Відображення в Grafana | дашборд «Кав'ярня: замовлення» |
| 5 | Дослідження логів через Grafana Loki | Loki + Promtail |
| 6 | Дослідження трейсів через Grafana Tempo | Tempo + OpenTelemetry |
| 7 | Сервер авторизації (Python + SQLite) | `auth-service`, токени JWT |
| 8 | Контейнеризація Docker | усі компоненти в Docker Compose |
| 9 | Обмін повідомленнями між сервісами | RabbitMQ |

## Бачення (корисність)

**Назва:** Інформаційна система обробки замовлень кав'ярні.

**Проблема.** У години пік замовлень стає більше, ніж бариста встигає приготувати.
Якщо каса напряму чекає на бариста, то збій або затримка на одному етапі зупиняє всю роботу.
Власник також не бачить, скільки замовлень чекає і де виникає затримка.

**Кому потрібна система:**

| Учасник | Тип | Що отримує |
|---|---|---|
| Клієнт (касир) | основна дійова особа | швидко оформлює замовлення |
| Бариста | основна дійова особа | отримує замовлення по черзі |
| Власник кав'ярні | основна дійова особа | бачить графіки й отримує сповіщення |
| Адміністратор | допоміжна дійова особа | запускає систему та стежить за сервісами |

**Користь.** Замовлення приймаються, навіть коли бариста тимчасово не працює, і не губляться.
Власник бачить стан роботи в реальному часі.

## Оцінка ефекту від впровадження (лекція 10)

Відповіді на запитання «Скільки ми втратимо, якщо відмовимося?» та «Який ефект від реалізації системи?».

**Усі числа нижче умовні.** Це приклад розрахунку для типової невеликої кав'ярні, у реальному проєкті їх треба замінити фактичними даними.

| Показник | Значення |
|---|---|
| Замовлень за день | 100 |
| Частка загублених або втрачених через черги | 5 % (5 замовлень) |
| Середній чек | 65 грн |
| **Втрати без системи за день** | 5 × 65 = 325 грн |
| **Втрати без системи за місяць (30 днів)** | 325 × 30 = 9 750 грн |
| Частка втрат, яку усуває система | 50 % |
| Збережений дохід за місяць | 4 875 грн |
| Витрати на обслуговування за місяць | 1 500 грн |
| **Чистий ефект за місяць** | 4 875 − 1 500 = 3 375 грн |

Програмне забезпечення системи відкрите, тому плати за ліцензії немає.

## Порівняння з існуючими рішеннями (лекція 3)

| Варіант | Переваги | Недоліки для нашої задачі |
|---|---|---|
| Папір або усна передача | не потребує витрат | замовлення губляться, немає статистики |
| Таблиця Excel або Google Forms | просто й швидко | немає черги, контролю обробки та сповіщень |
| Готова POS-система (наприклад, Poster, Syrve) | багато функцій, готові каса й облік | платна передплата, закрита внутрішня будова, зайві для малого закладу функції |
| **Власна система** | лише потрібні функції, відкритий код, повний контроль | потрібне обслуговування, немає каси та обліку складу |

Для реального закладу готова POS-система часто буде практичнішою. Власну систему обрано, бо мета проєкту полягає у проєктуванні й реалізації мікросервісної архітектури.

## Нефункціональні вимоги (властивості)

| № | Вимога |
|---|---|
| НФВ-1 | Система запускається однією командою `docker compose up -d --build` |
| НФВ-2 | Зупинка barista-service не заважає приймати нові замовлення |
| НФВ-3 | Замовлення зберігаються в черзі після перезапуску RabbitMQ (durable-черга, persistent-повідомлення) |
| НФВ-4 | Метрики оновлюються не рідше ніж раз на 5 секунд |
| НФВ-5 | Алерт спрацьовує не пізніше ніж через 1 хвилину після проблеми |
| НФВ-6 | Веб-інтерфейси доступні лише з цього комп'ютера (127.0.0.1) |
| НФВ-7 | Кожен сервіс має власний обліковий запис RabbitMQ із мінімальними правами, вхід `guest` вимкнено |
| НФВ-8 | Система працює в окремому virtual host `coffee` |
| НФВ-9 | Замовлення та меню доступні лише з дійсним токеном, Grafana лише після входу |
| НФВ-10 | Паролі в сервері авторизації зберігаються лише у вигляді хешу |
| НФВ-11 | Недоступність PostgreSQL не призводить до втрати замовлень: вони очікують у черзі |

### Обсяг робіт

**Входить:** авторизація, прийом замовлення, черга, імітація приготування, збереження в PostgreSQL, метрики, логи, трейси, алерти.

**Не входить:**

| Функція | Причина виключення |
|---|---|
| Оплата | висока вартість інтеграції, не впливає на основний ланцюжок |
| Облікові записи покупців | у системі входять лише працівники, покупцям вхід не потрібен |
| Мобільний застосунок | не реалізується в межах навчального терміну |
| Облік складу | окрема підсистема, не потрібна для демонстрації архітектури |

Виключення цих функцій не залишає без даних жодну функцію на діаграмах IDEF0.

## Чому RabbitMQ, а не Kafka

| Критерій | RabbitMQ | Kafka |
|---|---|---|
| Завдання проєкту | черга завдань: кожне замовлення виконує один бариста | потік подій, які читають багато споживачів |
| Після обробки | повідомлення видаляється | повідомлення зберігається |
| Підтвердження обробки | вбудоване (ack) | через зсув (offset) |
| Простота запуску | один контейнер із веб-панеллю | складніше налаштування кластера |

Обмеження навчальної версії: якщо RabbitMQ недоступний, нове замовлення отримує помилку 503.
Лекція 9 пропонує для цього випадку зберігати події в базі й надсилати їх пізніше, але для навчального проєкту це ускладнення не потрібне.
Паролі в конфігурації навчальні й придатні лише для локального запуску.
