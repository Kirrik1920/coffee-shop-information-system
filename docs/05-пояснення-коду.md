# 5. Пояснення коду простими словами

## Загальна ідея

| У кав'ярні | У проєкті |
|---|---|
| Перепустка працівника | токен JWT від `auth-service` |
| Касир | `order-service` |
| Полиця із замовленнями | черга RabbitMQ |
| Бариста | `barista-service` |
| Журнал виконаних замовлень | база PostgreSQL |
| Лічильники | метрики Prometheus |
| Щоденник подій | логи Loki |
| Маршрутний лист замовлення | трейс Tempo |
| Табло для власника | Grafana |
| Тривожний дзвінок | Alertmanager |

Касир не чекає, поки бариста зробить каву: він кладе замовлення на полицю й одразу приймає наступне.

## auth-service (`services/auth-service/app.py`)

Сервер авторизації зберігає користувачів у SQLite.

| Частина коду | Що робить |
|---|---|
| `init_db()` | створює таблицю та початкових користувачів |
| `login()` | перевіряє пароль і видає токен на 60 хвилин |
| `register()` | додає користувача, доступно лише адміністратору |
| `verify()` | показує, чи дійсний токен |
| `require_token` | не пропускає запити без дійсного токена |

Паролі зберігаються як хеш (`generate_password_hash`), тому їх не видно навіть у базі.

Токен JWT підписаний секретним ключем. Сервіси знають цей ключ і перевіряють підпис самостійно, не звертаючись щоразу до сервера авторизації. Тому вже виданий токен працює, навіть якщо auth-service тимчасово зупинено.

## order-service (`services/order-service/app.py`)

| Частина коду | Що робить |
|---|---|
| `MENU` | перелік напоїв і цін |
| `require_token` | перевіряє токен користувача |
| `publish()` | надсилає повідомлення в RabbitMQ разом із контекстом трейса |
| `create_order()` | обробляє `POST /orders`: перевіряє дані, формує повідомлення, викликає `publish()` |
| `metrics()` | віддає метрики на `/metrics` |

Коди відповідей: **202** замовлення прийнято, **400** помилка в даних, **401** немає дійсного токена, **503** RabbitMQ недоступний.

У `publish()` важливі такі рядки:
- `inject(headers)`: додає до повідомлення номер трейса;
- `virtual_host=RABBIT_VHOST`: підключення до окремого простору `coffee`;
- `delivery_mode=2`: повідомлення зберігається на диску;
- `confirm_delivery()`: сервіс чекає підтвердження, що брокер отримав повідомлення.

## RabbitMQ (`rabbitmq/definitions.json`)

Файл описує все, що RabbitMQ створює під час запуску:

- virtual host `coffee`;
- трьох користувачів із різними правами;
- exchange `coffee` і чергу `orders`, яка не зникає після перезапуску (`durable: true`);
- exchange `coffee.dead` і чергу `orders.invalid` для зіпсованих повідомлень.

Сервіси не створюють черг самостійно й не мають на це права: `order_service` може лише публікувати, а `barista_service` лише читати чергу `orders`.

## barista-service (`services/barista-service/worker.py`)

| Частина коду | Що робить |
|---|---|
| `ensure_db()` | підключається до PostgreSQL і створює таблицю |
| `already_done()` | перевіряє, чи замовлення вже виконано |
| `save_order()` | записує виконане замовлення |
| `is_text()` | перевіряє, що значення є текстом, який можна зберегти |
| `parse_message()` | перевіряє типи та допустимі значення всіх полів повідомлення |
| `handle_order()` | обробляє одне повідомлення |
| `consume()` | підключається до черги й чекає повідомлень |
| `main()` | запускає метрики й перепідключається, якщо RabbitMQ або PostgreSQL недоступні |

Порядок дій у `handle_order()`:

1. Перевірити повідомлення функцією `parse_message()`. Якщо JSON зіпсований, поле має неправильний тип або значення поза межами, відхилити повідомлення (`basic_nack`), і RabbitMQ перекладе його в чергу `orders.invalid`.
2. Продовжити трейс за контекстом із заголовків повідомлення.
3. Якщо таке замовлення вже є в базі, просто підтвердити його. Це і є ідемпотентність.
4. «Приготувати»: пауза 2–4 секунди, час записується в метрику.
5. Зберегти в PostgreSQL.
6. Надіслати підтвердження (`basic_ack`).

Якщо PostgreSQL недоступний, замовлення повертається в чергу (`basic_nack` із `requeue=True`) і виконається пізніше.

`prefetch_count=1` означає, що бариста бере наступне замовлення лише після завершення попереднього.

**Чому `basic_ack` стоїть в кінці?** Якщо сервіс впаде під час приготування, RabbitMQ не отримає підтвердження й поверне замовлення в чергу.

## Метрики

| Метрика | Значення |
|---|---|
| `coffee_orders_created_total` | скільки замовлень прийнято |
| `coffee_orders_processed_total` | скільки виконано |
| `coffee_order_processing_seconds` | час приготування |
| `coffee_db_insert_seconds` | час запису в PostgreSQL |
| `coffee_db_errors_total` | помилки запитів до бази |
| `coffee_auth_logins_total` | успішні та невдалі спроби входу |
| `coffee_orders_unauthorized_total` | запити без дійсного токена |
| `coffee_orders_duplicate_total` | пропущені повторні доставки |
| `coffee_orders_failed_total` | відхилені повідомлення |
| `pg_up`, `pg_stat_database_*`, `pg_database_size_bytes` | робота PostgreSQL (`postgres-exporter`) |
| `rabbitmq_queue_messages` | довжина черги (метрика самого RabbitMQ) |
| `up` | чи доступний сервіс для Prometheus |

Лічильники зберігаються в пам'яті сервісу й обнуляються при перезапуску. Тому в Grafana використано функцію `increase()`, яка враховує такі обнулення.

## Логи (Loki)

Сервіси просто друкують повідомлення. Promtail читає логи контейнерів із міткою `logging: promtail` і надсилає їх у Loki. У Grafana логи шукаються запитом, наприклад `{service="barista-service"}`.

Рядки логів містять `trace_id`, тому з рядка можна перейти до відповідного трейса.

## Трейси (Tempo)

Один трейс показує шлях замовлення:

`POST /orders` → `rabbitmq publish` → `process order` → `prepare drink` → `postgres insert`

У Grafana: Explore → Tempo → запит `{resource.service.name="order-service"}`.

## docker-compose.yml

Файл описує 12 контейнерів і запускає їх однією командою. `depends_on` із `service_healthy` змушує сервіси чекати, поки RabbitMQ і PostgreSQL будуть готові. `volumes` зберігають дані між перезапусками.

## Можливі запитання на захисті

**Чому брокер, а не прямий HTTP-запит?**
Касир не залежить від бариста: якщо бариста не працює, замовлення чекають у черзі.

**Як влаштована авторизація?**
Користувач надсилає логін і пароль в auth-service та отримує підписаний токен JWT. order-service перевіряє підпис і термін дії токена.

**Навіщо і метрики, і логи, і трейси?**
Метрики показують, що є проблема. Логи пояснюють, що саме сталося. Трейс показує, на якому кроці й скільки часу зайняла обробка конкретного замовлення.

**Як збираються метрики PostgreSQL?**
`postgres-exporter` читає системні таблиці СУБД і віддає дані у форматі Prometheus.

**Що станеться, якщо PostgreSQL впаде?**
Замовлення приймаються, але не зберігаються: вони повертаються в чергу, спрацьовує алерт `PostgresDown`. Коли база запрацює, замовлення виконаються.

**Що станеться, якщо RabbitMQ впаде?**
Нові замовлення отримають відповідь 503, а ті, що вже в черзі, збережуться на диску. barista-service кожні 3 секунди намагається підключитись знову і сам продовжує роботу.

**Чому RabbitMQ, а не Kafka?**
Тут потрібна черга завдань, де кожне замовлення виконує один бариста і після цього воно не потрібне. Kafka краще підходить для потоку подій, які читають багато споживачів.

**Чому в кожного сервісу свій обліковий запис?**
Так видно, який сервіс підключений, а права обмежені: якщо один сервіс зламають, він не зможе виконувати дії іншого.

**Що відбувається із зіпсованим повідомленням?**
Воно не губиться: RabbitMQ переміщує його в чергу `orders.invalid`, спрацьовує алерт `InvalidOrdersDetected`, а адміністратор може його переглянути.

**Як система захищена від повторної доставки?**
Кожне замовлення має унікальний `id`, а бариста перевіряє його в базі перед обробкою.
