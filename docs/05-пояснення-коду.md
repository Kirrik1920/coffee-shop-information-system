# 5. Пояснення коду простими словами

## Загальна ідея

Кав'ярня складається з касира, полиці із замовленнями та бариста.

| У кав'ярні | У проєкті |
|---|---|
| Касир | `order-service` |
| Полиця із замовленнями | черга RabbitMQ |
| Бариста | `barista-service` |
| Журнал виконаних замовлень | база SQLite |
| Лічильники | метрики Prometheus |
| Табло для власника | Grafana |
| Тривожний дзвінок | Alertmanager |

Касир не чекає, поки бариста зробить каву: він кладе замовлення на полицю й одразу приймає наступне.

## order-service (`services/order-service/app.py`)

| Частина коду | Що робить |
|---|---|
| `MENU` | перелік напоїв і цін |
| `Counter(...)` | лічильники для Prometheus |
| `publish()` | підключається до RabbitMQ і надсилає повідомлення |
| `create_order()` | обробляє `POST /orders`: перевіряє дані, формує повідомлення, викликає `publish()` |
| `metrics()` | віддає метрики на `/metrics` |

Коди відповідей: **202** замовлення прийнято, **400** помилка в даних, **503** RabbitMQ недоступний.

У `publish()` важливі такі рядки:
- `virtual_host=RABBIT_VHOST`: підключення до окремого простору `coffee`;
- `delivery_mode=2`: повідомлення зберігається на диску;
- `confirm_delivery()`: сервіс чекає підтвердження, що брокер отримав повідомлення.

## RabbitMQ (`rabbitmq/definitions.json`)

Файл описує все, що RabbitMQ створює під час запуску:

- virtual host `coffee`;
- трьох користувачів із різними правами;
- exchange `coffee` і чергу `orders`, яка не зникає після перезапуску (`durable: true`);
- exchange `coffee.dead` і чергу `orders.invalid` для зіпсованих повідомлень.

Сервіси не створюють черг самостійно й не мають на це права: `order_service` може лише публікувати, а `barista_service` лише читати чергу `orders`.

## barista-service (`services/barista-service/worker.py`)

| Частина коду | Що робить |
|---|---|
| `init_db()` | створює таблицю в SQLite |
| `already_done()` | перевіряє, чи замовлення вже виконано |
| `save_order()` | записує виконане замовлення |
| `parse_message()` | перевіряє, що всі поля повідомлення мають правильний тип |
| `handle_order()` | обробляє одне повідомлення |
| `consume()` | підключається до черги й чекає повідомлень |
| `main()` | запускає метрики й перепідключається, якщо RabbitMQ недоступний |

Порядок дій у `handle_order()`:

1. Перевірити повідомлення функцією `parse_message()`. Якщо JSON зіпсований або поле має неправильний тип, відхилити повідомлення (`basic_nack`), і RabbitMQ перекладе його в чергу `orders.invalid`.
2. Якщо таке замовлення вже є в базі, просто підтвердити його. Це і є ідемпотентність.
3. «Приготувати»: пауза 2–4 секунди, час записується в метрику.
4. Зберегти в базу.
5. Надіслати підтвердження (`basic_ack`).

`prefetch_count=1` означає, що бариста бере наступне замовлення лише після завершення попереднього.

**Чому `basic_ack` стоїть в кінці?** Якщо сервіс впаде під час приготування, RabbitMQ не отримає підтвердження й поверне замовлення в чергу.

## Метрики

| Метрика | Значення |
|---|---|
| `coffee_orders_created_total` | скільки замовлень прийнято |
| `coffee_orders_processed_total` | скільки виконано |
| `coffee_order_processing_seconds` | час приготування |
| `coffee_orders_duplicate_total` | пропущені повторні доставки |
| `coffee_orders_failed_total` | відхилені повідомлення |
| `rabbitmq_queue_messages` | довжина черги (метрика самого RabbitMQ) |
| `up` | чи доступний сервіс для Prometheus |

Лічильники зберігаються в пам'яті сервісу й обнуляються при перезапуску.
Тому в Grafana використано функцію `increase()`, яка враховує такі обнулення.

## docker-compose.yml

Файл описує 6 контейнерів і запускає їх однією командою.
`depends_on` із `service_healthy` змушує сервіси чекати, поки RabbitMQ буде готовий.
`volumes` зберігають дані між перезапусками.

## Можливі запитання на захисті

**Чому брокер, а не прямий HTTP-запит?**
Касир не залежить від бариста: якщо бариста не працює, замовлення чекають у черзі.

**Що станеться, якщо RabbitMQ впаде?**
Нові замовлення отримають відповідь 503, а ті, що вже в черзі, збережуться на диску. barista-service кожні 3 секунди намагається підключитись знову і сам продовжує роботу, коли брокер запрацює.

**Чому RabbitMQ, а не Kafka?**
Тут потрібна черга завдань, де кожне замовлення виконує один бариста і після цього воно не потрібне. Kafka краще підходить для потоку подій, які читають багато споживачів.

**Як масштабувати систему?**
Запустити кілька копій бариста: `docker compose up -d --scale barista-service=2`. Для цього спочатку треба прибрати публікацію порту 8001, бо дві копії не можуть зайняти один порт, і перейти зі SQLite на спільну базу, розраховану на кілька клієнтів.

**Чому в кожного сервісу свій обліковий запис?**
Так видно, який сервіс підключений, а права обмежені: якщо один сервіс зламають, він не зможе виконувати дії іншого.

**Що відбувається із зіпсованим повідомленням?**
Воно не губиться: RabbitMQ переміщує його в чергу `orders.invalid`, спрацьовує алерт `InvalidOrdersDetected`, а адміністратор може його переглянути.

**Як система захищена від повторної доставки?**
Кожне замовлення має унікальний `id`, а бариста перевіряє його в базі перед обробкою.
