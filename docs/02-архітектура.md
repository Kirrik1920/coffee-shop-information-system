## Як проходить замовлення

1. Користувач входить через `POST /login` в auth-service і отримує токен JWT.
2. Клієнт надсилає `POST /orders` із токеном в order-service.
3. order-service перевіряє токен і дані, починає трейс і кладе повідомлення в RabbitMQ разом із контекстом трейса.
4. Exchange `coffee` за ключем `orders.created` направляє повідомлення в чергу `orders`.
5. barista-service бере одне замовлення (`prefetch_count=1`), продовжує той самий трейс і «готує» замовлення кілька секунд.
6. Сервіс записує результат у PostgreSQL і лише тоді надсилає RabbitMQ підтвердження (ack). Зіпсоване повідомлення RabbitMQ переміщує в чергу `orders.invalid`. Якщо PostgreSQL недоступний, замовлення повертається в чергу.
7. Prometheus кожні 5 секунд забирає метрики сервісів, RabbitMQ і `postgres-exporter`.
8. Promtail збирає логи контейнерів у Loki, а трейси надходять у Tempo.
9. Grafana показує метрики, логи й трейси, а Alertmanager отримує алерти.

## Формат повідомлення (за лекцією 9)

```json
{
  "id": "d0482898-5a6f-4c90-95d8-aecb35f3bf2d",
  "name": "OrderCreated",
  "time": "2026-11-09T09:36:15+00:00",
  "data": { "drink": "latte", "quantity": 1, "customer": "Олена" }
}
```

## Рішення і причини

| Рішення | Причина |
|---|---|
| Асинхронний зв'язок через брокер | приймання замовлень не залежить від швидкості бариста (лекція 6) |
| PostgreSQL в окремому контейнері | клієнт-серверна СУБД, яку вимагає завдання (лекція 1) |
| `postgres-exporter` | метрики роботи СУБД без зміни коду бази (лекція 4) |
| Сервер авторизації з токенами JWT | доступ лише для авторизованих, сервіси перевіряють токен без звернення до БД користувачів |
| Хеш паролів замість самих паролів | витік файлу не розкриває паролі |
| Loki і Promtail | логи всіх сервісів в одному місці |
| OpenTelemetry і Tempo | видно шлях замовлення через усі сервіси |
| Передача контексту трейса в заголовках повідомлення | трейс не обривається на брокері |
| Ручне підтвердження (ack) після збереження | замовлення не загубиться при збої сервісу |
| Повернення в чергу при помилці БД | замовлення виконається, коли PostgreSQL запрацює |
| Перевірка `id` перед обробкою | RabbitMQ може доставити повідомлення повторно, а обробка має бути ідемпотентною (лекція 9) |
| Durable-черга і persistent-повідомлення | замовлення переживають перезапуск брокера |
| Окрема база для кожного сервісу | PostgreSQL для замовлень, SQLite для користувачів (лекція 11) |
| Окремий virtual host `coffee` | стандартний vhost не використовується (лекція 9) |
| Власний обліковий запис для кожного сервісу | видно, хто підключений, а права мінімальні (лекція 9) |
| Черга `orders.invalid` | зіпсовані повідомлення не губляться і доступні для аналізу (лекція 8) |

## Принципи мікросервісної архітектури (лекція 11)

| Принцип | Як реалізовано |
|---|---|
| Індивідуальна відповідальність | auth-service авторизує, order-service приймає, barista-service виконує |
| Децентралізація даних | PostgreSQL належить barista-service, SQLite належить auth-service |
| Розумні сервіси, прості з'єднання | логіка в сервісах, брокер лише передає повідомлення |
| Незалежне розгортання | кожен сервіс має власний образ і перезапускається окремо |
| Ізоляція відмов | зупинка barista-service не заважає приймати замовлення |

## Звідки взято рішення (прецедентний підхід)

| Частина проєкту | Приклад курсу |
|---|---|
| СУБД у Docker і експортер метрик | Практики 2, 3 (`3mysql`) |
| Сервер авторизації на Python і SQLite | Практика 4, `temperature` |
| Сервіси на Python у контейнерах | Практика 4, `temperature` |
| Трейси в Tempo | Практичний приклад до лекції 4 |
| Prometheus, Grafana, метрики RabbitMQ | Практика 9, `Rabbitmq.Prometheus` |
| Правила алертів і Alertmanager | Лекція 5, Практика 5 |
| Exchange, черга, binding | Лекція 9, Практика 8 |

Логи в Loki вимагає завдання курсу, готового прикладу в практиках немає.
