## Як проходить замовлення

1. Клієнт надсилає `POST /orders` в order-service.
2. order-service перевіряє напій за меню та кладе повідомлення в RabbitMQ.
3. Exchange `coffee` за ключем `orders.created` направляє повідомлення в чергу `orders`.
4. barista-service бере одне замовлення (`prefetch_count=1`) і «готує» його кілька секунд.
5. Сервіс зберігає результат у SQLite і лише тоді надсилає RabbitMQ підтвердження (ack).
6. Prometheus кожні 5 секунд забирає метрики всіх сервісів.
7. Grafana показує графіки, а Alertmanager отримує алерти.

## Формат повідомлення (за лекцією 9)

```json
{
  "id": "d0482898-5a6f-4c90-95d8-aecb35f3bf2d",
  "name": "OrderCreated",
  "time": "2026-11-09T09:36:15+00:00",
  "data": { "drink": "latte", "quantity": 1, "customer": "Олена" }
}
```

## Рішення і причини

| Рішення | Причина |
|---|---|
| Асинхронний зв'язок через брокер | приймання замовлень не залежить від швидкості бариста (лекція 6) |
| Ручне підтвердження (ack) після збереження | замовлення не загубиться при збої сервісу |
| Перевірка `id` перед обробкою | RabbitMQ може доставити повідомлення повторно, а обробка має бути ідемпотентною (лекція 9) |
| Durable-черга і persistent-повідомлення | замовлення переживають перезапуск брокера |
| Окрема база лише в barista-service | кожен мікросервіс має власне сховище (лекція 11) |
