# 6. Контракт сервісів (лекція 11)

Контракт описує інтерфейс сервісу, вхідні й вихідні параметри та можливі помилки.

## Постачальники, споживачі, реєстр

| Роль | Хто виконує |
|---|---|
| Постачальник авторизації | auth-service |
| Постачальник HTTP API | order-service |
| Споживач HTTP API | клієнт (касир), Prometheus |

## HTTP API auth-service

Базова адреса: `http://localhost:8002`

### POST /login

| Поле | Тип | Обов'язкове |
|---|---|---|
| `username` | рядок | так |
| `password` | рядок | так |

Успішна відповідь, код 200:

```json
{ "access_token": "<JWT>", "token_type": "Bearer", "expires_in": 3600 }
```

| Код | Причина |
|---|---|
| 400 | немає полів або вони не є текстом |
| 401 | неправильний логін або пароль |

### POST /register

Потрібен токен користувача з роллю `admin`.

| Поле | Тип | Обов'язкове | Умова |
|---|---|---|---|
| `username` | рядок | так | 3–50 символів |
| `password` | рядок | так | 8–128 символів |
| `role` | рядок | ні, типово `cashier` | `cashier` або `admin` |

| Код | Причина |
|---|---|
| 201 | користувача створено |
| 400 | неправильні дані |
| 401 | немає дійсного токена |
| 403 | токен не адміністратора |
| 409 | такий користувач уже існує |

### GET /verify

Потрібен токен. Повертає `username` і `role`, код 200, або 401.

### GET /health, GET /metrics

Стан сервісу та метрики у форматі Prometheus.

## HTTP API order-service

Базова адреса: `http://localhost:8000`

`GET /menu` і `POST /orders` потребують заголовка `Authorization: Bearer <токен>`. Без дійсного токена відповідь 401.

### GET /menu

Повертає напої та ціни. Код відповіді: 200.

```json
{ "americano": 50, "cappuccino": 65, "espresso": 45, "latte": 70, "tea": 35 }
```

### POST /orders

| Поле | Тип | Обов'язкове | Умова |
|---|---|---|---|
| `drink` | рядок | так | значення з меню |
| `quantity` | ціле число | ні, типово 1 | від 1 до 10 |
| `customer` | рядок | ні, типово `гість` | текст у кодуванні UTF-8, до 100 символів, без символу NUL |

Успішна відповідь, код 202:

```json
{ "order_id": "d0482898-5a6f-4c90-95d8-aecb35f3bf2d", "status": "accepted" }
```

| Код | Причина |
|---|---|
| 400 | тіло не є коректним JSON, напою немає в меню, неправильна кількість або `customer` не є допустимим текстом |
| 401 | немає дійсного токена |
| 503 | RabbitMQ недоступний |

### GET /health, GET /metrics

Стан сервісу та метрики у форматі Prometheus.

## Подія OrderCreated

| Параметр | Значення |
|---|---|
| Virtual host | `coffee` |
| Exchange | `coffee`, тип direct |
| Ключ маршрутизації | `orders.created` |
| Черга | `orders` |
| Кодування | JSON, UTF-8 |
| Збереження | durable-черга, persistent-повідомлення |
| Заголовки | `traceparent` для продовження трейса |

| Поле | Тип | Опис |
|---|---|---|
| `id` | рядок UUID | унікальний номер, потрібен для захисту від повторної обробки |
| `name` | рядок | завжди `OrderCreated` |
| `time` | рядок ISO 8601 | час створення |
| `data.drink` | рядок | напій |
| `data.quantity` | ціле число | кількість, від 1 до 10 |
| `data.customer` | рядок | клієнт |

Поля `id`, `data.drink` та `data.quantity` обов'язкові, `time` і `data.customer` можуть бути відсутні.

**Обробка помилок.** barista-service перевіряє типи та допустимі значення всіх полів. Некоректне повідомлення відхиляється і через exchange `coffee.dead` потрапляє в чергу `orders.invalid`.

## Топологія та права RabbitMQ

Усе описано у файлі `rabbitmq/definitions.json`.

| Користувач | Призначення | Налаштування | Запис | Читання |
|---|---|---|---|---|
| `coffee` | адміністратор, веб-панель | усе | усе | усе |
| `order_service` | публікація замовлень | немає | exchange `coffee` | немає |
| `barista_service` | отримання замовлень | немає | немає | черга `orders` |

## База даних PostgreSQL

База `coffee`, таблиця `orders`:

| Поле | Тип | Опис |
|---|---|---|
| `id` | TEXT, первинний ключ | номер замовлення |
| `drink` | TEXT | напій |
| `quantity` | INTEGER | кількість |
| `customer` | TEXT | клієнт |
| `created_at` | TEXT | час створення |
| `done_at` | TEXT | час виконання |
