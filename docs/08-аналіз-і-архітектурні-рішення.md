# 8. Аналіз предметної області та архітектурні рішення

Документ показує, як методи та правила з лекцій 2, 3, 7, 8 і 11 застосовано в проєкті.

## Методи інформаційного аналізу (лекція 2)

### Когнітивний аналіз

| Етап | Застосування в проєкті |
|---|---|
| Ідентифікація об'єкта з урахуванням досвіду | Кав'ярня розглядається як потік замовлень від каси до бариста |
| Дослідження джерел даних | Джерело одне: замовлення з напоєм, кількістю та клієнтом. Дані перевіряються, бо можуть бути неправильними |
| Вимірювання станів об'єкта | Метрики: прийнято, виконано, довжина черги, час приготування |
| Моделювання поведінки та стійкості | Перевірено поведінку під час зупинки бариста, RabbitMQ і приймання замовлень |
| Аналіз навколишнього середовища | Години пік збільшують кількість замовлень, робота бариста обмежує швидкість |
| Модель управління | Порогові значення алертів сигналізують, коли втрутитись |
| Самоорганізація системи | Черга автоматично згладжує різницю між швидкістю прийому та виконання |
| Сценарний аналіз | Сценарії: звичайна робота, час пік, збій сервісу, збій брокера, зіпсовані дані |

### Моделювання

| Модель | Де наведена |
|---|---|
| Функціональна | діаграми IDEF0 |
| Архітектурна | діаграми C4 |
| Поведінкова | сценарії використання, `01-мета-та-вимоги.md` |
| Інформаційна | формат події та таблиця `orders`, `06-контракт-сервісів.md` |
| Модель безпеки | права користувачів RabbitMQ, `06-контракт-сервісів.md` |

### Системний аналіз: властивості системи

| Властивість | Опис |
|---|---|
| Назва | Система обробки замовлень кав'ярні |
| Мета | Передавати замовлення від прийому до виконання без втрат |
| Склад | order-service, RabbitMQ, barista-service, SQLite, Prometheus, Grafana, Alertmanager |
| Внутрішня структура | сервіси пов'язані брокером, моніторинг збирає дані з усіх |
| Ступінь формалізації | вимоги, контракт і правила алертів описані в документах та конфігурації |
| Стійкі стани | працює; бариста недоступний; брокер недоступний; черга перевантажена |

## Аналіз метасистеми (лекція 3)

| Операція | Результат |
|---|---|
| 1. Яка більша система (метасистема) містить нашу | Робота кав'ярні як закладу |
| 2. Склад метасистеми | Каса й обслуговування, приготування, закупівля та склад, облік і фінанси, персонал |
| 3. Роль нашої системи | Забезпечує інформаційний зв'язок між обслуговуванням і приготуванням, а також дає власнику дані про роботу |

Зв'язки із закупівлею, складом та фінансами винесено за межі проєкту.

## Класифікація архітектурних рішень (лекція 7)

| Вид архітектури | Рішення в проєкті |
|---|---|
| Бізнес-архітектура | процес: прийняти замовлення → поставити в чергу → приготувати → контролювати |
| Інформаційна | події `OrderCreated`, база виконаних замовлень, часові ряди метрик |
| Прикладна | order-service, barista-service, RabbitMQ, Prometheus, Grafana, Alertmanager |
| Технічна | Docker, Docker Compose, Python, Windows 10 із WSL 2, засоби моніторингу та розмежування прав |

## Відповіді на питання про архітектуру (лекція 7)

| Питання | Відповідь |
|---|---|
| Що? | Система передачі й контролю виконання замовлень |
| Як? | Через асинхронний обмін повідомленнями між мікросервісами |
| Де? | У контейнерах Docker на одному комп'ютері |
| Коли? | Працює постійно, метрики оновлюються кожні 5 секунд |
| Хто? | Користуються клієнт (касир), бариста, власник, адміністратор |
| Чому саме так? | Прийом замовлень не має залежати від швидкості та стану бариста |
| Які потрібні ресурси? | Наведено в розділі «Ресурси» файлу `01-мета-та-вимоги.md` |

## Шари архітектури LSA (лекція 7)

Проєкт малий, тому шари показано спрощено.

| Шар | Реалізація |
|---|---|
| Первинні дані (Primary Data) | order-service приймає й перевіряє замовлення |
| Брокер між шарами | RabbitMQ |
| Ядро (Core Data) | barista-service застосовує правила обробки та зберігає результат |
| Аналітичні вітрини (Data Mart) | панелі Grafana |
| Сервісний шар (Service) | Prometheus та Alertmanager: контроль, діагностика та оповіщення |

## Патерни обміну повідомленнями (лекція 8)

| Патерн | Реалізація |
|---|---|
| Message, Event Message | подія `OrderCreated` |
| Message Channel | черга `orders` |
| Point-To-Point | кожне замовлення виконує один споживач |
| Canonical Data Model | спільний формат JSON |
| Channel Adapter | бібліотека pika |
| Messaging Gateway | функція `publish()` |
| Guaranteed Delivery | durable-черга, persistent-повідомлення, підтвердження |
| Event-Driven Consumer | `basic_consume` із функцією `handle_order` |
| Durable Subscriber | підтвердження зберігає стан обробки, необроблене залишається в черзі |
| Idempotent Receiver | перевірка `id` у функції `already_done()` |
| Invalid Message Channel, Dead Letter Channel | черга `orders.invalid` |

## Ризики проєкту (лекції 2, 11)

| Ризик | Імовірність | Вплив | Заходи |
|---|---|---|---|
| Нереалістичні терміни | середня | високий | поетапна розробка, спочатку основний ланцюжок |
